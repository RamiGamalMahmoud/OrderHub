# OrderHub — مرجع تنفيذ دورة الطلب والتوصيل والتاريخ والأرشفة

## حالة الوثيقة وطريقة استخدامها

- هذه الوثيقة هي المرجع الموحد للقرارات المعتمدة وتعليمات التنفيذ.
- إنشاء الوثيقة لا يجيز بدء تنفيذ الميزة؛ يبدأ التنفيذ عند طلب المستخدم ذلك.
- عند التنفيذ تُقرأ الوثيقة كاملة، وتُراجع تعليمات المستودع وحالة الملفات قبل التعديل.
- تُنفذ المهام بالترتيب. كل مهمة وحدة عمل ذات نتيجة قابلة للتحقق، ولا يبدأ العمل في التالية قبل اجتياز بوابة قبول الحالية.
- المهام مراحل تطوير، وليست إصدارات مستقلة للنشر. لا تُشغّل نسخة جزئية ضد قاعدة التشغيل، ولا تبقى مسارات قديمة مخالفة في الإصدار النهائي.
- لا تُنشأ commits أو branches أو PRs ولا تُطبّق migrations على قاعدة التشغيل إلا ضمن تفويض المستخدم.
- لا يُوسّع النطاق عشوائيًا. تُصلح الأخطاء الموجودة في المسارات المتأثرة والمشاكل الناتجة عن التغيير. تُوثق المشاكل المستقلة ويُحدد أثرها.
- لا يُطلب اعتماد القرارات المحسومة هنا مرة أخرى. تُسأل فقط أسئلة جديدة مؤثرة لا تحسمها الوثيقة أو الأدلة الحالية.

## 1. الهدف والنطاق

تنفيذ دورة تشغيلية موحدة للطلب، تشمل الحالة، تشغيل خطوات التوصيل، الفشل وإعادة المحاولة، الإلغاء، التسليم المباشر، التاريخ، الأرشفة، حماية التعارض، وترحيل البيانات القديمة.

يشمل النطاق Domain / Application / Infrastructure / Web والاختبارات والعقود والقراءات ومسارات الكتابة المرتبطة.

خارج إعادة التصميم:

- Invoice / Quotation / Proforma workflows وPDF وصلاحيات المستندات.
- Document indicators مثل `IsInvoiced`.
- Inventory وSalla والتكاملات الخارجية.
- نظام مالي أو احتساب تعويض المندوبين.
- Event Sourcing وWorkflow Engine والبنية العامة لإدارة الحالات.

خروج المستندات من النطاق لا يعفي من الحفاظ على ارتباطاتها وقراءتها بعد الأرشفة، أو اختبار استكمال المسودة وربط مستنداتها عند إنشاء الطلب.

## 2. مبادئ التنفيذ

1. أقل تصميم صحيح ومقروء يطبق القواعد ويحفظ البيانات.
2. إعادة استخدام الخدمات والسياق والصلاحيات الحالية، خصوصًا `ICurrentUser` وRequestExecutor وMediatR وUnitOfWork.
3. Domain مصدر قواعد الانتقال والقفل والتسلسل والمزامنة. Application تنسق العملية والمستخدم والوقت والحفظ. Web تعرض القواعد ولا تعيد اختراعها.
4. لا Command أو Interface أو helper لكل انتقال بلا حاجة. لا طبقات أو محركات أو message broker جديدة.
5. لا تاريخ عام لكل تعديل على كل كيان؛ المطلوب تاريخ الحالة والخطوة وبيانات الأرشفة.
6. أسماء واضحة ودوال ذات مسؤولية محددة. التعليقات تشرح السبب أو القيد باختصار، ولا تكرر الكود.
7. لا يُحتفظ بمسار مفتوح مثل `SetStatus(anyValue)` يمكنه تجاوز القواعد.
8. لا تُعطّل اختبارات صحيحة أو تُخفّف قيود البيانات لتجاوز فشل. تُحدث الاختبارات التي تثبت سلوكًا أصبح مخالفًا للقرارات.
9. لا يُقبل العمل النهائي مع أخطاء معروفة غير معالجة في المسارات المتأثرة.

## 3. القرارات التجارية المعتمدة

### 3.1 حالات الطلب

| القيمة | العرض |
|---|---|
| `Processing` | قيد التجهيز |
| `ReadyForPickup` | جاهز للتسليم |
| `OutForDelivery` | خرج للتوصيل |
| `Shipped` | تم الشحن |
| `DeliveryFailed` | تعذر التسليم |
| `Delivered` | تم التسليم |
| `Cancelled` | تم الإلغاء |

- الطلب الجديد يبدأ صراحةً بـ`Processing`.
- لا يستخدم اسم `Preparing` بدلًا منه.
- تُزال `Pending` من حالات الطلب بعد معالجة بياناتها ومراجع استخدامها.
- `Pending` تظل حالة صحيحة للخطوة؛ لا تُحوّل حالة الخطوة إلى `Processing`.
- لا توجد حالة «تم إصدار بوليصة» أو حالة أخرى للمستندات. إنشاء الفاتورة لا يغير حالة الطلب.
- لا توجد حالة `Retry`، ولا إعادة فتح للطلب.
- `Delivered` و`Cancelled` نهائيتان.
- الأرشفة ليست قيمة في `OrderStatus`.

### 3.2 مسارات الطلب

| الطريقة | المسار الطبيعي | الفشل وإعادة المحاولة |
|---|---|---|
| `Pickup` | `Processing → ReadyForPickup → Delivered` | لا يوجد مسار فشل حاليًا |
| `DeliveryMan` | `Processing → OutForDelivery → Delivered` | `OutForDelivery → DeliveryFailed → OutForDelivery` |
| `ShippingCompany` | `Processing → Shipped → Delivered` | `Shipped → DeliveryFailed → Shipped` |
| `DeliveryChain` | `Processing → OutForDelivery → Delivered` | الفشل وإعادة المحاولة على الخطوة |

- الإلغاء مسموح من كل حالة غير نهائية بسبب إلزامي.
- لا قفز بين الحالات، ولا رجوع للتجهيز بعد بدء التنفيذ.
- فشل خطوة سلسلة لا يجعل الطلب `DeliveryFailed`.
- إعادة المحاولة تعود للحالة المناسبة للطريقة، ولا تضيف milestone جديدة.
- يُرفض التشغيل أو التعديل للطلب المؤرشف.

### 3.3 قفل بيانات الطلب

التعديل مسموح فقط عندما يكون الطلب `Processing` وغير مؤرشف.

القفل يبدأ عند `ReadyForPickup` أو `OutForDelivery` أو `Shipped`، ويستمر عند الفشل وإعادة المحاولة وفي الحالات النهائية.

يشمل العميل والمصدر والمنتجات والخصائص والكميات والأسعار والضريبة والموردين والدفع وطريقة التوصيل والجهات المعينة وبنية الخطوات وترتيبها.

القفل لا يمنع العمليات التشغيلية المسموحة. تُفصل قابلية تعديل البيانات عن توفر إجراءات التشغيل؛ لا يستخدم `IsLocked` مبهم لتعطيل كل شيء.

ينطبق القفل على كل مسار كتابة، بما فيه `ChangePaymentMethodCommand`، وعلى حفظ محرر قديم بعد بدء التنفيذ بواسطة مستخدم آخر.

### 3.4 حالات الخطوة والتسلسل

الحالات: `Pending`, `InProgress`, `Completed`, `Failed`, `Cancelled`.

المسار العادي: `Pending → InProgress → Completed`.

المحاولة الفاشلة: `InProgress → Failed → InProgress`.

يشترط تشغيل الخطوة:

- طلب `DeliveryChain` في `OutForDelivery` وغير مؤرشف.
- انتماء الخطوة لنفس الطلب وصحة حالتها وجهة تنفيذها.
- اكتمال جميع الخطوات السابقة حسب `StepOrder`.

اكتمال الخطوة يتيح التالية ولا يبدأها تلقائيًا. الفاشلة تمنع التالية. لا يجوز أكثر من خطوة نشطة في سلسلة صحيحة.

لا يشترط أن تكون أرقام الترتيب متصلة؛ `10, 20, 30` ترتيب صالح.

يمكن حفظ خطة ناقصة أثناء التجهيز، لكن بدء السلسلة يتطلب خطة صالحة غير فارغة وجهات تنفيذ صالحة.

`Completed` محمية من كل رجوع أو إلغاء عادي. `Cancelled` لا تُستأنف. إلغاء الخطوة ليس إجراءً مستقلًا في التشغيل العادي؛ يأتي من إلغاء الطلب أو التسليم المباشر.

### 3.5 المزامنة

- إكمال جميع خطوات سلسلة غير فارغة يغير الطلب تلقائيًا إلى `Delivered`.
- إلغاء الطلب يحافظ على `Completed` ويلغي `Pending` و`InProgress` و`Failed` مع تاريخها وسبب إلغاء الطلب.
- تحفظ الحالة والتاريخ وكل الخطوات المتأثرة ونسخة الطلب في عملية ذرية.
- لا يُنشأ حدث مكرر أو استدعاء متكرر للمزامنة بسبب callbacks متداخلة.

### 3.6 التسليم المباشر

يسمح لطلب سلسلة في `OutForDelivery` بخطة صالحة غير فارغة.

تعرض جميع الخطوات. المكتملة سابقًا للقراءة فقط. لكل خطوة غير مكتملة يختار المستخدم:

- إبقاء الحالة الحالية، وهو الاختيار الافتراضي.
- `Completed`.
- `Failed`.
- `Cancelled`.

سبب التسليم المباشر إلزامي. اختيار الفشل أو الإلغاء يحتاج سببًا للخطوة؛ يجوز استخدام السبب العام إذا اختاره المستخدم صراحةً، دون نسخ صامت أو اختلاق سبب.

تُراجع كل الاختيارات قبل أي تعديل: المعرفات والملكية والتكرار والحالات والنسخة والأسباب. الطلب لا يحدد بنفسه المستخدم أو التوقيت أو مصدر التاريخ.

تُسجل التغييرات الفعلية فقط، دون اختلاق `InProgress` وسيطة. تُفصل هذه العملية عن الإكمال العادي حتى لا تسلّم الطلب أثناء معالجة أول اختيار.

بعد التسليم، تبقى الخطوات غير المكتملة بحالاتها وتاريخها، وتُقفل كل الخطوات ضد التشغيل وتخرج من المهام النشطة. لا تُكمل أو تُلغى تلقائيًا.

اكتمال كل الخطوات يؤدي إلى تسليم الطلب، لكن تسليم الطلب لا يعني بالضرورة اكتمال كل الخطوات.

### 3.7 الأسباب

سبب إلزامي للتسليم المباشر والأرشفة والإلغاء وفشل تسليم الطلب وفشل أو إلغاء الخطوة.

الحد الأقصى 200 حرف. يُرفض `null` والنص الفارغ والمسافات فقط، مع تطبيع واضح للمسافات الخارجية. يتحقق السيرفر من القاعدة، ولا يعتمد على عداد الشاشة وحده.

### 3.8 الأرشفة

| الوضع | القاعدة |
|---|---|
| `Processing` | يمكن الأرشفة بسبب وتأكيد |
| بدأ التنفيذ وما زال غير نهائي | يجب الإلغاء أولًا |
| `Delivered` أو `Cancelled` | يمكن الأرشفة |
| مؤرشف | لا أرشفة مكررة ولا استعادة |

الأرشفة تخفي الطلب من القائمة التشغيلية الافتراضية، وتبقيه في سجل المؤرشف للقراءة. تحفظ البيانات والخطوات والتاريخ والمستندات، ولا تغير الحالة التشغيلية أو حالات الخطوات.

تُحفظ هوية من أرشف والاسم وقت العملية والوقت والسبب. يمكن تمثيل ذلك بحقول محمية على الطلب؛ لا يحتاج جدول أحداث عام جديد لمجرد الأرشفة مرة واحدة.

يُمنع تعديل المؤرشف وتشغيله واستعادته وحذفه فعليًا. تظل المستندات المرتبطة قابلة للقراءة، وتظل الارتباطات التاريخية مانعة لحذف الكيانات المرتبطة.

## 4. التاريخ والتوقيت والتعارض

### 4.1 سجلان مستقلان

`OrderStatusHistory` و`DeliveryStepStatusHistory` كيانان فعليان بتهيئة EF مناسبة.

حقول الحدث: المعرف، الطلب، الخطوة عند الحاجة، الحالة السابقة والجديدة، الوقت UTC، المستخدم واسم عرضه وقت العملية، السبب، المصدر، نسخة الطلب بعد العملية.

- الأحداث لا تُعدل أو تحذف في العمليات العادية.
- مصدر الحدث يميز التشغيل العادي وإعادة المحاولة والتسليم المباشر والإلغاء والمزامنة والترحيل، بتعريف واحد غير ملتبس.
- لا event عند مجرد إنشاء خطوة `Pending` في خطة جديدة.
- تعديل البيانات بلا تغيير حالة لا يضيف حدث حالة.
- حالة لم تتغير لا تحصل على حدث جديد.
- هوية جهة التنفيذ لا تختلط بهوية مستخدم النظام.
- لا ترث سجلات التاريخ تلقائيًا أدوات تعديل التوقيت العامة الموجودة في `ModelBase`.

### 4.2 إنشاء الطلب

يُحفظ الطلب بحالة `Processing`، ويُضاف حدث `null → Processing` بنفس `CreatedAt` بالضبط وبالمستخدم الحالي، في نفس الحفظ.

لا تتغير ذرية استكمال المسودة وربط مستنداتها وحذف مسودة المستخدم.

### 4.3 الوقت

يُنشأ وقت واحد من السيرفر لكل عملية، ويُحفظ UTC في `timestamp with time zone`، وتستخدمه كل الأحداث الناتجة عنها.

يُعرض حسب منطقة المستخدم من المتصفح، مع التوقيت الصيفي. لا يُستخدم وقت المتصفح لتأريخ الحدث، ولا `ToLocalTime()` على السيرفر باعتباره وقت المستخدم.

تتحول حدود فلاتر الأيام المحلية إلى UTC. ترتيب القراءة ثابت بالنسخة ومعرف الحدث عند الحاجة، لا الوقت وحده.

### 4.4 النسخة

تشارك كل الكتابات المؤثرة في نسخة الطلب: تعديل البيانات والدفع والخطة والحالة والخطوات والأرشفة. تغيير خطوة يحدث النسخة حتى لو لم تتغير حالة الطلب.

ترسل العمليات النسخة المقروءة، ويُفرض التعارض عند الحفظ في قاعدة البيانات، وليس بمقارنة مبكرة فقط.

- التعارض يرفض العملية كلها دون تاريخ أو آثار جزئية.
- لا إعادة تنفيذ تلقائية بعد تحديث القراءة.
- نفس الحالة بنسخة حديثة لا تولد حدثًا أو زيادة نسخة بلا تغيير فعلي.
- الطلب بنسخة قديمة يُرفض حتى لو أصبحت الحالة مطابقة.
- تُميز أخطاء التحقق والانتقال والتعارض والحفظ وإلغاء التنفيذ.

## 5. البيانات القديمة

### 5.1 السياسة المعتمدة

| الطلب القديم | الحالة بعد الترحيل | تاريخ الطلب | الخطوات إن وجدت |
|---|---|---|---|
| غير مكتمل وغير ملغى | `Processing` | `null → Processing` عند تاريخ إنشاء الطلب | `Pending` |
| مكتمل | `Delivered` | `null → Processing` عند الإنشاء، ثم `Processing → Delivered` بعد ثانية | `Completed` |
| ملغى | `Cancelled` | `null → Processing` عند الإنشاء، ثم `Processing → Cancelled` بعد ثانية | `Cancelled` |

جعل جميع خطوات القديم الملغى `Cancelled` استثناء ترحيل فقط. الإلغاء الجديد يحافظ على المكتمل.

### 5.2 الحفاظ على البيانات

- لا تتغير IDs أو `CreatedAt` للطلبات والخطوات أو علاقات العميل والمستندات والمنتجات.
- لا تغير الكميات والأسعار والضريبة وأسماء المنتجات والموردين وقيم الخصائص المحفوظة.
- تُحتفظ الحالة الأصلية قبل تحويلها، خصوصًا `Shipped → Processing`، في بيانات الترحيل المناسبة دون إنشاء نظام تدقيق عام.
- تُميز السجلات الناتجة عن الترحيل. الفارق ثانية للترتيب، وليس وقت تسليم أو إلغاء فعليًا.
- لا يُختلق مستخدم أو سبب أو محاولة قديمة.
- استثناء السبب والمستخدم يخص الترحيل فقط، ولا يضعف قواعد العمليات الجديدة.
- لا تنشأ خطوات لطلب ليس له خطوات.
- لا تنشأ سلسلة أحداث تنفيذ مفترضة للخطوات القديمة. تُمثل الحالة النهائية المهيأة كأساس ترحيل عند الحاجة، دون ادعاء تنفيذ فعلي أو وقت تنفيذ معروف.
- وقت الإنشاء الأصلي للخطوة يبقى كما هو؛ لا يُعاد تأريخها لإجبار توافقها مع الوقت الاصطناعي لتاريخ الطلب.
- اكتمال مرحّل ليس دليلًا ماليًا على قيام جهة معينة بالعمل.
- الترحيل لا يتكرر ولا يضيف سجلات مكررة عند إعادة المحاولة.

تُفحص القيم غير الصالحة والتواريخ غير القابلة للاستخدام والعلاقات الناقصة قبل الترحيل، ولا تُحذف أو تُصحح صامتًا.

## 6. التصميم التقني وحدود المسؤولية

### Domain

`Order` ينسق الانتقالات والخطوات والقفل والمزامنة والأرشفة وحماية المكتمل، ويُنشئ حقائق التاريخ بالوقت والمستخدم المقدمين من Application.

تُحمى حقول الخطوات من الكتابة المباشرة المخالفة. يُستخدم enum واحد لحالة الخطوة ومصدر أحداث واضح.

### Application

عمليات قليلة وواضحة للحالات والخطوات والتسليم المباشر والأرشفة. إعادة استخدام `ICurrentUser` والصلاحيات الحالية، دون خدمة مستخدم موازية.

كل عملية تتحقق من البيانات والنسخة، وتحمل aggregate المطلوب، وتستدعي Domain ثم تحفظ. نتائج الحفظ توفر ما يلزم لتحديث الحالة والمعرفات والنسخة دون مطابقة غير آمنة بواسطة ترتيب قابل للتغير.

`Orders.Read` لقراءة الحالة والتاريخ والخطوات والأرشيف. `Orders.Write` للعمليات. تجاوز Admin للصلاحيات لا يتجاوز قواعد العمل.

### Infrastructure

تهيئة الجداول والعلاقات والفهارس والنسخة والحفظ والقراءات والترحيل. استخدام نفس DbContext للكتابة والتاريخ.

تُحمى سجلات التاريخ من الحذف المتتابع غير المقصود. تُراجع العلاقات مع المستخدم والطلب والخطوة والمستندات وفحوص استخدام الكيانات بعد الأرشفة.

لا يضاف فلتر عالمي يخفي المؤرشف من كل العلاقات بلا مراجعة. تُفصل القراءات التشغيلية والأرشيفية، وتبقى فحوص الارتباطات شاملة المؤرشف.

### Web

عرض الحالة والتعليمات والأسباب والتأكيدات والتوقيت المحلي. لا dropdown عام للحالة، ولا قواعد انتقال مستقلة عن Domain/Application.

القراءة التشغيلية تكون صغيرة، وتحمل الحالة والطريقة والنسخة وقابلية تعديل البيانات والإجراءات وموانعها والخطوات. لا DTO عملاق أو framework للتعليمات. النصوص وتنسيق العرض في Web، مع إعادة استخدام أوصاف enum الحالية حيث تناسب.

## 7. واجهة المستخدم المعتمدة

### 7.1 صفحة التفاصيل

صفحة `/orders/{id}` تبقى ملخصًا للطلب والعميل والمنتجات والمعلومات التجارية الحالية. يُطور قسم التوصيل ليعرض الطريقة والجهة والحالة وآخر حدث تشغيلي وشريط مراحل مختصر وملخص الفشل.

زر `متابعة دورة الطلب` للطلب القابل للتشغيل، و`عرض دورة الطلب والسجل` للنهائي والمؤرشف أو العرض للقراءة فقط.

### 7.2 شاشة التشغيل

مسار مقترح `/orders/{id}/workflow`، مع رابط رجوع للتفاصيل، ويحتوي:

1. ملخص مدمج وشريط مراحل حسب الطريقة.
2. بطاقة المطلوب الآن والتعليمات والإجراء الأساسي.
3. الجاهزية أثناء التجهيز وموانع البدء الحقيقية.
4. جميع خطوات السلسلة وحالاتها وموانع تشغيلها.
5. سجل الطلب، وتاريخ الخطوة عند الطلب.

لا يحمل الملخص التاريخ الكامل. تُستخدم قراءة التاريخ المقسمة أو التحميل عند الطلب.

### 7.3 الإجراءات والتعليمات

- أسماء واضحة حسب الطريقة: `جاهز للاستلام`، `بدء التوصيل`، `تسجيل الشحن`، `بدء سلسلة التوصيل`.
- في السلسلة الإجراء الرئيسي للخطوة المتاحة، وليس فشل الطلب كله.
- `Pending` المتاحة تعرض بدء الخطوة؛ المقفلة تعرض سبب القفل.
- `InProgress` تعرض إكمال الخطوة أو تسجيل التعذر؛ `Failed` تعرض إعادة المحاولة.
- المكتملة والملغاة والخطوات داخل طلب نهائي أو مؤرشف لا تعرض تشغيلًا.
- لا تُعرض خطوة لاحقة كإجراء قبل تحقق شروطها.
- توفر العمليات يتحدد بالصلاحية والقواعد. القراءة فقط تُوضح دون أزرار كتابة.

### 7.4 شريط المراحل والخطوات

الشريط يوضح المسار ولا يمثل التاريخ. الفشل استثناء، والـRetry لا يكرر milestones. الإلغاء يظهر كنهاية، ولا يعرض التسليم كمرحلة قادمة.

الطلب المسلّم بخطوات غير مكتملة يعرض ذلك بوضوح؛ لا تصبح كل البطاقات خضراء تلقائيًا.

تستخدم الخطوات بياناتها الحالية: رقم الخطوة ونوع الجهة واسمها والحالة. أمثلة المستودع والفرع ليست خصائص جديدة تُضاف أو تُستنتج دون بيانات.

تُميز اسم الجهة عن المستخدم الذي سجّل العملية. رقم المحاولة يُشتق من التاريخ الحقيقي عند الحاجة، ولا تُحسب أحداث الترحيل محاولات.

### 7.5 الحوارات

- فشل أو إلغاء: أثر العملية وسبب إلزامي وعدّاد 200 حرف.
- إلغاء الطلب: توضيح حفظ المكتمل وإلغاء غير المكتمل ونهائية الطلب.
- التسليم المباشر: جميع الخطوات، المكتملة للقراءة فقط، الاختيارات المعتمدة، الأسباب، ملخص نتائج، وتوضيح قفل كل الخطوات بعد التسليم.
- يمكن اختصار اختيار إكمال الجميع، لكن لا يكون افتراضيًا ولا ينفذ الحفظ تلقائيًا.
- زر التأكيد: `تأكيد تسليم الطلب بهذه النتائج`، مع رجوع دون تغيير.
- أرشفة: حفظ البيانات ومنع التشغيل والتعديل والاستعادة وسبب إلزامي.
- الأرشفة والإلغاء ضمن إجراءات ثانوية، وفق توفرهما، دون إخفاء إمكانية الإلغاء المطلوبة.

### 7.6 التاريخ والأرشيف والاستقرار

`آخر تحديث` في دورة الطلب مصدره الحدث التشغيلي المناسب، لا `ModifiedAt` العام. تغير الخطوة يظهر دون event وهمي للطلب.

التاريخ يعرض الوقت المحلي والمستخدم والسبب والمصدر بلغة مفهومة. المرحّل يظهر بعلامة واضحة ولا يوصف بأنه إثبات لوقت التنفيذ.

سجل مستقل للمؤرشف، مع الحالة التشغيلية الأصلية وعلامة أرشفة وبياناتها، وكل التفاصيل للقراءة دون استعادة.

أثناء الحفظ تُمنع الإجراءات المتعارضة والضغط المتكرر. تُحفظ المدخلات عند فشل الحفظ، وعند التعارض تُعاد القراءة وتُراجع الاختيارات قبل تأكيد جديد دون إعادة تنفيذ تلقائية.

تُعالج حالة المفقود والقراءة غير المصرح بها والبيانات القديمة الناقصة وموانع التشغيل، دون صفحة فارغة أو exception غير معالج.

### 7.7 المظهر

MudBlazor والـtheme الحالي وRTL. الأولوية لشاشة 1366×768 ثم الهاتف والتابلت. بطاقات مدمجة دون Stepper ضخم. ألوان وأيقونات ونصوص معًا، ودعم لوحة المفاتيح وfocus وتسميات الحقول.

CSS محدود، دون Bootstrap أو Tailwind أو مؤثرات غير لازمة. الحوارات الطويلة قابلة للتمرير وأثر العملية وأزرارها واضحان.

| فلتر قائمة الطلبات | الحالة المختارة لا تُرسل للاستعلام. ربطه فعليًا، وكذلك أي فلاتر معروضة متأثرة |
| `UnitOfWork` | خطأ persistence عام. تمييز تعارض النسخة ومعالجة CancellationToken والمعاملة |

ملاحظة مستقلة: توليد رقم الطلب يعتمد على قراءة آخر رقم ويحتمل التكرار عند الإنشاء المتزامن. يُفحص الأثر ويُعالج إذا أثّر على سلامة إنشاء الطلب في هذا النطاق، دون إعادة تصميم عامة للترقيم.

## 9. المهام التنفيذية وبوابات القبول

### بروتوكول كل مهمة

1. قراءة النطاق والمتطلبات والاعتماديات.
2. تنفيذ وحدة العمل كاملة، بما فيها أي تكيف ضروري للمتصلين بها حتى يبقى الحل قابلًا للبناء والاختبار.
3. تشغيل التحقق الملائم للتغيير ومراجعة الفروق. لا توسعة أو تكرار اختبارات بلا سبب.
4. إصلاح الإخفاقات المتعلقة بالمهمة، وتوثيق الإخفاقات السابقة المستقلة بالأدلة.
5. تحديث سجل التنفيذ أدناه بالنتيجة والأدلة والقيود.
6. الانتقال للتالية فقط بعد اجتياز بوابة القبول. انتهاء تعديل الملفات ليس اكتمال المهمة.

لا يحل تقسيم المهام محل اختبار الميزة ككل. لا تُنشر مراحل جزئية، وتُغلق كل طرق التوافق المؤقتة قبل القبول النهائي.

### Task 00 — خط الأساس وفحص البيانات وخريطة الأثر

**النتيجة:** معرفة ما سنغيره وما سنحافظ عليه وخطة التعامل مع بيانات المصدر.

**العمل:** مراجعة التعليمات والحالة الحالية، حصر الكتابات والقراءات والعقود والـenums والعلاقات والمigrations الفعلية، وقياس baseline للاختبارات. فحص قاعدة مستهدفة مصرح بها قراءةً فقط: الحالات والطريقة والمعرفات والتواريخ والخطوات والجهات والارتباطات والقيم غير الصالحة. إعداد مصفوفة Keep/Modify/Replace/Remove لكل مسار متأثر.

**التحقق:** لا تعديل بيانات. لا طباعة connection strings أو أسرار أو بيانات شخصية بلا حاجة. توثيق مصادر الفحص ومدى تطابق EF مع المخطط الفعلي.

**بوابة القبول:** خريطة أثر مكتملة وقرارات عملية للحالات غير الصالحة وخطة تحقق قبل/بعد الترحيل. إذا تعذر اتصال قاعدة المصدر، لا يُختلق audit؛ يمكن مراجعة الكود، لكن لا تعتبر جاهزية ترحيل المصدر مثبتة ولا تُطبق عليه migration.

### Task 01 — قواعد Domain والحالات والتاريخ

**النتيجة:** نموذج أعمال قابل للاختبار يطبق كل قواعد الحالة والخطوة والقفل والعمليات المركبة.

**العمل:** حالات الطلب والخطوة، التاريخ المحمي، مصدر الأحداث، هوية العملية، قواعد الطرق والتسلسل والأسباب والتسليم المباشر والإلغاء والأرشفة. إعادة استخدام `Order` وتجنب policy classes غير الضرورية. تكييف المتصلين بالقدر اللازم للبناء، دون ترك bypass نهائي.

**التحقق:** اختبارات الانتقالات المسموحة والممنوعة، الأسباب 200، القفل، حماية المكتمل، all-completed مع سلسلة غير فارغة، الفشل المتكرر، التسليم المباشر باختيارات مختلطة، الأرشفة وعدم الاستعادة، والرفض قبل أي mutation جزئي.

**بوابة القبول:** القواعد المعتمدة ممثلة باختبارات واضحة، والحل يبنى، ولا قواعد أعمال جديدة غير معتمدة أو تعقيد غير لازم.

### Task 02 — EF والمخطط والنسخة وحماية العلاقات

**النتيجة:** حفظ الحالة والتاريخ والنسخة والأرشفة بصورة متماسكة.

**العمل:** mappings وDbSets والجداول والفهارس وFKs وحماية النسخة. default Processing وتمثيل الحالات النصي. تصميم استثناء legacy في المستخدم والسبب دون فتحه للعمليات الجديدة. مراجعة read/write scope وUTC وdelete behavior.

**التحقق:** PostgreSQL معزول: حفظ وقراءة enums والتاريخ، nullable legacy، حدود الأسباب، FKs، concurrency لخطوة فقط، timestamps، ومنع حذف التاريخ. مراجعة فرق migration للحقول التجارية والـsnapshot وعدم إجراء تحويل كميات/أسعار ضمن هذه الميزة.

**بوابة القبول:** schema قابل للتطبيق على نسخة اختبار، واختبارات persistence ناجحة، ولا تغيير أو فقد غير مقصود في المخطط التجاري.

**قيد مهم:** لا يضاف قيد قاعدة بيانات يمنع الترتيب المؤقت المستخدم حاليًا عند تبديل الخطوات، مثل اشتراط rank موجب في كل statement، دون تكييف خوارزمية الترتيب واختبارها. تظل صحة الترتيب النهائي مفروضة، والمرحلة المؤقتة داخل معاملة لا يراها مستخدم التشغيل.

### Task 03 — ترحيل Legacy قابل للتحقق

**النتيجة:** تهيئة الطلبات القديمة وخطواتها وتاريخها حسب السياسة المعتمدة، دون تغيير الهوية والقيم.

**العمل:** ترحيل الحالات وdefault والتاريخ بفارق ثانية وتهيئة الخطوات ومعلومة المصدر والحالة الأصلية. منع تكرار baselines. معالجة نتائج audit دون حذف أو اختلاق بيانات. وضع سياسة ترتيب ونسخة واضحة لأحداث الأساس.

**التحقق:** نسخة PostgreSQL قديمة تحتوي Pending/Processing/Shipped/Delivered/Cancelled، طرق فارغة، سلاسل فارغة ومتعددة، ومستندات. مقارنة counts وIDs والقيم والعلاقات والتواريخ الأصلية قبل وبعد. اختبار إعادة المحاولة/عدم التكرار وفشل الترحيل وتراجعه. ترتيب Processing قبل final وعدم نسبة الأحداث لمستخدم وهمي.

**بوابة القبول:** كل فئات الترحيل صحيحة، ولا فقد بيانات، ولا تشغيل production. لا حذف للمigrations التاريخية؛ لا Down مدمر للتاريخ كبديل عن خطة استعادة.

### Task 04 — إنشاء الطلب وتحديثه والدفع والمسودات

**النتيجة:** كل كتابة للبيانات الأساسية متوافقة مع القفل والتاريخ والنسخة.

**العمل:** Processing وحدث البداية بنفس CreatedAt وهوية حقيقية. Update/Draft completion/Payment، validation للمدخلات، الحفاظ على step sync والمعاملة والقيم المحفوظة، نتيجة حفظ موثوقة للمعرفات والنسخة. معالجة المفقود والأسباب البرمجية للأخطاء.

**التحقق:** إنشاء عادي ومن مسودة، atomic linking للمستندات، حفظ متكرر، IDs ثابتة، إضافة/حذف/تبديل rank، قفل كل حالة عدا Processing، payment bypass، نسخة قديمة، عدم تعديل tracked aggregate عند التحقق الفاشل، rollback بعد staging rank، ومدخلات ناقصة دون runtime exception غير معالج.

**بوابة القبول:** دورة create/read/edit/save/reload صحيحة، وكل تحديث ممنوع يُرفض دون أي أثر جزئي.

### Task 05 — عمليات الحالة والخطوات والتسليم المباشر

**النتيجة:** use cases تشغيلية كاملة تحفظ آثارها وتاريخها ونسختها.

**العمل:** عمليات قليلة للحالة والخطوة والتسليم المباشر مع trusted actor/time والتحميل المناسب. إزالة/استبدال handlers القديمة وReturnToPending وأي طريق تغيير مباشر. تمييز النتائج والتمرير الصحيح لـCancellationToken.

**التحقق:** لكل طريقة، retry، failure، step ownership، sequencing، same-operation time/user، آخر خطوة، إلغاء جزئي يحفظ completed، direct delivery مختلط وأسباب لكل نتيجة، no-op حديث وstale conflict، وإكمال/فشل/إلغاء متزامن بسياقين مستقلين.

**بوابة القبول:** كل عملية atomic، ولا مسار تشغيلي قديم يخالف القواعد، ولا استكمال تلقائي للخطوات عند direct delivery.

### Task 06 — الأرشفة وإغلاق الحذف الفعلي

**النتيجة:** أرشفة غير قابلة للاستعادة تحفظ البيانات والارتباطات.

**العمل:** الأمر وسلوك Domain وسبب ومستخدم ووقت ونسخة. منع active-after-start قبل الإلغاء. إزالة command/entry للحذف الفعلي أو تحويل مدخله بوضوح للعملية الجديدة بعقدها، دون fallback للحذف. مراجعة فحوص استخدام العملاء والمنتجات والجهات والمستندات.

**التحقق:** Processing/final مسموح، active مرفوض، no restore، repeated archive، archive/write conflict، counts وIDs والعلاقات ثابتة، المستندات readable، والفحوص تشمل المؤرشف.

**بوابة القبول:** لا كتابة أو حذف أو استعادة للمؤرشف، ولا فقد أو اختفاء غير مقصود في العلاقات التاريخية.

### Task 07 — القراءات التشغيلية والتاريخ والأرشيف

**النتيجة:** عقود صغيرة تخدم التفاصيل والتشغيل والقائمة والأرشيف دون تكرار القواعد.

**العمل:** الحالة والطريقة والنسخة وقابلية تعديل البيانات والإجراءات وموانعها والجاهزية والخطوات. تاريخ مقسم وثابت الترتيب، معلومات latest event، read-only archived. معالجة null/missing والبيانات غير الصالحة بأمان. ربط الفلاتر بما تعرضه الشاشة.

**التحقق:** جميع الحالات والطرق، nullable legacy، نهائي بخطوات غير مكتملة، user snapshot، legacy marker، source labels، pagination بلا تكرار/فقد، استبعاد المؤرشف من التشغيل فقط، وصلاحيات Read/Write.

**بوابة القبول:** قراءات آمنة ومتناسقة مع Domain، ولا تحميل تاريخ كامل في list/summary، ولا queries مفرطة أو DTO عام متضخم.

### Task 08 — صفحة التفاصيل وشاشة التشغيل والخطوات

**النتيجة:** يستطيع المستخدم معرفة أين وصل الطلب وماذا يفعل ولماذا بعض الخطوات غير متاحة.

**العمل:** صفحة details ملخصًا، workflow مستقلة، stage card وتعليمات وأزرار حسب الطريقة، readiness، كل steps، lock reasons، روابط التنقل والتاريخ عند الطلب. حالات loading/missing/forbidden/legacy/archived، وإعادة التحميل الصحيحة عند تغير route.

**التحقق:** Read-only، قفل البيانات دون قفل التشغيل المتاح، chain بلا order failure، Pending action/blocked، mobile/RTL/1366×768، لون+أيقونة+نص وkeyboard، الحالة النهائية mixed steps، وغياب الخصائص المخترعة كأسماء warehouse/branch.

**بوابة القبول:** الواجهة تعرض الإجراءات الصحيحة وتشرح القفل والخطوة التالية، دون قواعد workflow منفصلة أو ازدحام Details.

### Task 09 — الحوارات والتاريخ والأرشيف والتوقيت المحلي

**النتيجة:** العمليات المؤثرة مفهومة قبل الحفظ ويمكن مراجعة نتائجها وتاريخها.

**العمل:** failure/cancel/direct/archive dialogs، أسباب 200، effects summary، preserve default direct choices، حماية completed، سجل الطلب والsteps والمؤرشف، timezone من المتصفح، double submit وconflict refresh والاحتفاظ بالمدخلات عند الفشل.

**التحقق:** direct مع إبقاء Pending/InProgress/Failed، source والتاريخ بعده، no hidden auto-complete، cancellation effects، archive شرط Processing والاستثناء للنشط، no restore، timezone/DST، scrolling/focus، conflict أثناء الحوار وعدم تنفيذ الاختيارات القديمة تلقائيًا.

**بوابة القبول:** المستخدم يرى كل الأثر قبل التأكيد، النتائج تطابق السيرفر، ولا يعرض التاريخ المرحّل كدليل تنفيذ فعلي.

### Task 10 — إغلاق التوافق القديم والاختبارات الشاملة

**النتيجة:** نسخة نهائية واحدة متوافقة، بلا bypass أو سلوك قديم منافس.

**العمل:** بحث شامل في الحل ونقاط الدخول والمشروعات القديمة عن enum/commands/mutations/delete/توقيت وافتراضات مخالفة. تحديث اختبارات السلوك القديم، مراجعة النطاق والفروق والأسماء والتعليقات وازدواجية القواعد، وإزالة أدوات التوافق المؤقتة.

**التحقق:** build والتحقق العام الملائم، اختبارات end-to-end تشغيلية وإنشاء/تحرير Processing/دفع/مسودة ومستندات، PostgreSQL atomicity/concurrency/migration/archive. مثال يجب تحديثه: اختبار مزامنة قديم يعدل طلبًا Delivered؛ يصبح تعديلًا لطلب Processing مع اختبار رفض النهائي، دون إلغاء اختبار IDs.

**بوابة القبول:** لا مدخل نشط يخالف التصميم، ولا runtime error معروف غير معالج في المسارات المتأثرة. تُذكر الإخفاقات المستقلة السابقة بالأدلة ولا تُخفى. لا تغيير مستندات أو تجريدات غير لازمة.

### Task 11 — تجربة الانتقال وخطة الإصدار وتسليم الأدلة

**النتيجة:** إثبات انتقال آمن على نسخة مماثلة وخطة إصدار قابلة للمراجعة.

**العمل:** نسخة احتياطية وتحقق من الاستعادة، rehearsal مع schema/history الفعليين، مقارنة قبل/بعد، ترتيب تطبيق schema/code وإيقاف الكتابة القديمة، فحوص صحة بعد الإصدار وخطة تراجع تحافظ على التاريخ. تقرير الإنجاز وحدود التحقق.

**التحقق:** الطلبات والخطوات والمنتجات والمستندات والمستخدمون وعلاقاتهم، حالات الترحيل، new create history timestamp، التشغيل مع legacy، no duplicate baselines، وعدم استمرار نسخة قديمة ككاتب.

**بوابة القبول:** الأدلة والتقرير وخطة الإصدار مكتملة. نشر/apply على قاعدة التشغيل خطوة منفصلة ضمن تفويض المستخدم، وليس أثرًا تلقائيًا للاختبارات. لا يُدعى فحص production إذا لم يحدث.

## 10. تعريف اكتمال الميزة

- كل القواعد في القسم 3 مطبقة من السيرفر ومغطاة باختبارات مناسبة.
- لا يمكن تجاوز القفل أو التاريخ أو النسخة بواسطة command قديم أو UI قديمة أو مدخل نشط.
- الحالات والأرشفة والتاريخ والخطوات محفوظة دون partial commit.
- معرفات الطلب والخطوات والقيم التجارية والمستندات لا تضيع أو تتغير بالترحيل.
- الواجهة واضحة ومطابقة للقواعد ومناسبة للابتوب والهاتف والصلاحيات المختلفة.
- legacy وmissing/null والتعارض والأخطاء لها نتائج مفهومة، لا exceptions غير معالجة.
- المستندات والمسودات والارتباطات المتوافقة مستمرة في العمل.
- الكود مقروء ومنظم، والتعقيد والأصناف الجديدة في الحد الضروري.
- لا تضخم نطاق أو إعادة تصميم غير مبررة، ولا أخطاء معروفة في المسارات المتأثرة متروكة للقبول النهائي.
- فحص قاعدة المصدر وتجربة الترحيل وخطة الإصدار موثقة بحدودها الحقيقية.
