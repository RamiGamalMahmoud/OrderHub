# إصدار دورة الطلب والتوصيل

هذه تعليمات الإصدار بعد تنفيذ المهام 00–11. لم تُطبّق migrations على قاعدة التطوير الأصلية أو قاعدة التشغيل أثناء التنفيذ. تفويض التنفيذ الحالي شمل الكود والاختبارات وcommits، وليس نشر الخدمة أو ترحيل قاعدة التشغيل.

## 1. النسخة المطلوب إصدارها

- إصدار Web الجديد ومكتبتي Application وInfrastructure وDomain معًا.
- لا تشغّل إصدارًا قديمًا يكتب الطلبات، سواء Web أو WPF أو أي عملية خلفية. كتابة الطلبات في مصدر WPF المتقاعد أُغلقت؛ بناءه ونشره خارج الحل الحالي ليسا جزءًا من الإصدار.
- المستندات والفواتير لا تغيّر حالة الطلب. لا تُضف حالة بوليصة أو مستند إلى هذا الإصدار.
- الوصول من الهاتف والتابلت متاح وفق الواجهة المتجاوبة المعتمدة. أُزيل حاجز User-Agent القديم؛ المصادقة والصلاحيات ما زالت مطلوبة.

## 2. التحضير قبل إيقاف الخدمة

1. تحقق من بيئة التشغيل المستهدفة، اسم القاعدة، آخر migration مطبّقة، حساب الخدمة، مسار بيانات التطبيق ومفاتيح تسجيل الدخول. لا تنقل connection strings أو بيانات العملاء إلى التقرير أو Git.
2. ابنِ النسخة المختبرة واحفظ نسخة الإصدار القديم وإعداداته. تأكد من أن مستخدم الخدمة يملك صلاحيات الملفات والمفاتيح والقاعدة المطلوبة.
3. كرر تجربة الاستعادة والترحيل على نسخة حديثة من القاعدة المستهدفة. دليل هذا التنفيذ يخص قاعدة التطوير المحلية فقط؛ لا يُفترض أن بيانات التشغيل مماثلة لها.
4. احفظ نسخة قاعدة PostgreSQL وجميع ملفات المستندات خارج القاعدة في مكان مؤمّن. النسخة المؤقتة التي استُخدمت في الاختبارات أُزيلت وليست نسخة تراجع تشغيلية.
5. قارن عدد الطلبات والخطوات والبنود والفواتير والمسودات والمستخدمين والعلاقات. تحقق من عدم وجود order_number مكرر أو تواريخ إنشاء NULL/infinity، ورتب خطوات مكررة أو غير موجبة، وجهات تنفيذ مفقودة أو علاقات يتيمة. لا تصحح أو تحذف بيانات تلقائيًا لإجبار الترحيل على النجاح.

أمثلة قراءة فقط قبل الإصدار:

```sql
SELECT migration_id FROM "__EFMigrationsHistory" ORDER BY migration_id;
SELECT order_status, count(*) FROM orders GROUP BY order_status ORDER BY order_status;
SELECT order_number, count(*) FROM orders GROUP BY order_number HAVING count(*) > 1;
SELECT id FROM orders WHERE created_at IS NULL OR NOT isfinite(created_at);
SELECT id FROM order_delivery_steps WHERE created_at IS NULL OR NOT isfinite(created_at) OR step_order <= 0;
SELECT order_id, step_order, count(*) FROM order_delivery_steps GROUP BY order_id, step_order HAVING count(*) > 1;
```

لا تحمل تجربة التطوير أي حالة Delivered/Cancelled؛ تغطية تحويل الحالات النهائية جاءت من اختبار PostgreSQL ببيانات اصطناعية تضم جميع الحالات القديمة، مع الاحتفاظ بالبند والفاتورة والمعرفات.

## 3. نافذة الإصدار وترتيب التنفيذ

1. امنع الكتابة مؤقتًا وأوقف جميع نسخ التطبيق القديمة والمهام التي تكتب الطلبات. لا تعتمد على تشغيل نسختين تتبادلان الكتابة أثناء الترحيل.
2. خذ النسخة الاحتياطية النهائية بعد توقف الكتابة، وافحص إمكانية استعادتها إلى قاعدة مختلفة. سجّل وقتها ومرجعها ومقاييس ما قبل الإصدار.
3. طبّق migrations على القاعدة المحددة صراحة، باستخدام حساب مخوّل، قبل بدء Web الجديد.
4. المخطط المطلوب، بالترتيب:

   - `20261006094846_RestrictSupplierProductLinks`: migration قديمة تم إصلاح اكتشافها؛ تمنع حذف مورد مستخدم.
   - `20261007011356_AddOrderLifecycleSchema`: التاريخ والنسخة والأرشفة وحالات الخطوات.
   - `20261007011638_InitializeLegacyOrderLifecycle`: تهيئة البيانات القديمة وفق القواعد المتفق عليها.
   - `20261007020026_ProtectOrderCreationIdentity`: هوية طلب الإنشاء وفهارس تفرد الهوية ورقم الطلب.

5. الملف [order-lifecycle-release.sql](order-lifecycle-release.sql) مولّد بـEF، idempotent، ويضم العملية كلها داخل transaction. جُرّب مرتين على نسخة مستعادة من المصدر. نقطة البداية له هي `20261006092315_RestrictPropertyDeletionForOrders`. إذا كان المخطط أقدم أو مختلفًا، ولّد ملفًا من نقطة البداية الفعلية وافحصه وجرّبه؛ لا تستخدم الملف على مخطط مجهول.
6. عند تشغيل SQL باستعمال psql، فعّل `ON_ERROR_STOP=1`، وحدد المضيف والقاعدة والمستخدم عبر بيئة آمنة. لا تضع كلمة المرور في الأوامر أو السجل. مثال بعد ضبط متغيرات PostgreSQL للهدف الصحيح:

```powershell
pg_dump --format=custom --no-owner --no-privileges --file=<protected-backup-path>
psql --set=ON_ERROR_STOP=1 --file=reports/order-lifecycle-release.sql
```

7. لا تبدأ التطبيق إذا فشل الترحيل أو بقي Pending في orders أو كانت مقارنة البيانات غير سليمة. احتفظ بدليل الفشل والنسخة الأصلية للتحليل.
8. شغّل Web الجديد بإعداداته ومكتباته المتوافقة، ثم تحقق من الصحة والمصادقة والقراءات. افتح الكتابة بعد نجاح الفحوص التالية.

## 4. فحوص القبول بعد الترحيل

- جميع معرفات الطلبات والخطوات والبنود والمستندات وcreated_at والكميات والأسعار والضريبة وبيانات snapshot محفوظة؛ لا تعديل للقيم التجارية بالترحيل.
- كل غير نهائي Processing، بما فيه Pending القديم. المكتمل يبقى Delivered والملغى يبقى Cancelled.
- لكل طلب قديم Processing بتاريخ إنشائه مع Source=LegacyMigration وOriginalStatus الأصلي. النهائي له سجل ثانٍ بعد ثانية واحدة؛ لا مستخدم أو سبب مختلق. خطوات النهائي Completed/Cancelled، وغير النهائي Pending؛ لا يُختلق تاريخ محاولات سابقة.
- كل طلب جديد له أول Processing بنفس created_at ومستخدم الإنشاء الحقيقي. إعادة إرسال الإنشاء نفسه لا تنشئ نسخة ثانية.
- التاريخ والأرشفة والنسخة والأثر على الخطوات يُحفظون معًا، ويُرفض تحديث نسخة قديمة دون أثر جزئي أو إعادة تنفيذ تلقائية.
- تغيير بيانات الطلب والدفع بعد بدء التسليم أو اكتماله أو إلغائه مرفوض من السيرفر؛ الواجهة توضّح السبب.
- سلسلة التوصيل تسير بالترتيب؛ فشل خطوة لا يفشل الطلب تلقائيًا؛ retry والتسليم المباشر يعملان حسب القواعد.
- التسليم المباشر يسمح بخطوات غير مكتملة، يحفظ اختيارات المستخدم، ويقفل تشغيل جميع الخطوات بعد تسليم الطلب.
- السبب مطلوب للفشل والإلغاء والأرشفة والتسليم المباشر، حتى 200 حرف بعد trim. إلغاء الطلب يلغي الخطوات غير المكتملة؛ المكتملة لا تتغير.
- الأرشفة تبقي الحالة والتاريخ والارتباطات، تخفي الطلب من التشغيل وتعرضه في سجل المؤرشف، دون استعادة أو تشغيل.
- Details والworkflow والتاريخ والقوائم والفواتير والمسودات وeditor تعالج missing/null والصلاحيات والتعارض بصورة مفهومة.
- وقت العمليات UTC من السيرفر؛ العرض بحسب منطقة المتصفح، بما فيها اختلاف التوقيت الصيفي.

قراءات سريعة بعد الإصدار:

```sql
SELECT count(*) FROM orders WHERE order_status = 'Pending'; -- صفر
SELECT count(*) FROM orders o WHERE NOT EXISTS (SELECT 1 FROM order_status_history h WHERE h.order_id=o.id); -- صفر
SELECT count(*) FROM order_status_history h JOIN orders o ON o.id=h.order_id
WHERE h.source='LegacyMigration' AND h.new_status='Processing' AND h.changed_at_utc <> o.created_at; -- صفر
SELECT order_status, count(*) FROM orders GROUP BY order_status;
SELECT status, count(*) FROM order_delivery_steps GROUP BY status;
```

راقب رسائل حفظ غير متوقعة وتعارضات النسخ وفشل المصادقة والمستندات وruntime errors خلال أول عمليات الاستخدام. التعارض المتوقع بين موظفين ليس مبررًا لإعادة تنفيذ العملية تلقائيًا.

## 5. التراجع دون إتلاف التاريخ

- لا تستخدم `database update` إلى migration سابقة كتراجع عادي. Down للتهيئة القديمة مرفوض، وDown للمخطط يرفض وجود التاريخ/الأرشفة، وDown لهوية الإنشاء يرفض إزالة مفاتيح مستخدمة.
- قبل فتح الكتابة الجديدة: إذا تعذر الإصدار، أوقفه، احتفظ بقاعدة التجربة الفاشلة للتحليل، واستعد النسخة النهائية إلى قاعدة أخرى، وافحصها ثم وجّه الإصدار القديم إليها. لا تستعد فوق القاعدة الوحيدة الموجودة دون حفظها.
- بعد فتح الكتابة الجديدة: الاستعادة إلى نسخة ما قبل الإصدار ستفقد عمليات حديثة. أوقف الكتابة وخذ نسخة كاملة من القاعدة الجديدة مع التاريخ والأرشفة؛ ابدأ بإصلاح أمامي. الرجوع إلى نسخة قديمة يتطلب قرارًا صريحًا وخطة لنقل العمليات الحديثة وحفظ دليلها، ولا يُنفّذ تلقائيًا.
- لا تشغّل الكود القديم ككاتب على المخطط الجديد. لا تحذف سجل الحالات أو تفك الأرشفة لتحسين التوافق.

## 6. إعادة إنتاج الأدلة

اختبارات PostgreSQL تستعمل قواعد عشوائية منفصلة تُزال بعد الاختبار. إعداد `ORDERHUB_REHEARSAL_SOURCE` هو opt-in لقراءة قاعدة مصدر وأخذ backup ثابت؛ `ORDERHUB_LIFECYCLE_TEST_POSTGRES` يحدد خادم إنشاء القواعد المعزولة. يوفّر `ORDERHUB_POSTGRES_BIN` مسار pg_dump/pg_restore، و`ORDERHUB_REHEARSAL_SQL` مسار SQL أعلاه، و`ORDERHUB_REHEARSAL_REPORT` مسار التقرير إن أريد حفظه.

اختبار `OrderLifecycleReleaseRehearsalTests` يستعيد النسخة، يقارن SHA-256 لكل أعمدة المصدر ما عدا order_status المتغير عمدًا وجدول migrations، ويجرّب ملف الإصدار وإعادته. عند ضبط `ORDERHUB_REHEARSAL_WEB_PROJECT` يشغّل Web من build Debug ضد النسخة المعزولة، ويختبر الدخول بUser-Agent هاتف وتحميل القوائم والتفاصيل والworkflow. بيانات الحساب والطلب هنا اصطناعية وتُزال مع القاعدة.

للمراجعة اليدوية فقط، يمكن ضبط `ORDERHUB_REHEARSAL_UI_SIGNAL` لمسار مؤقت: يظهر معرف الطلب في ملف `.ready`، وينتظر الاختبار ملف الإنهاء حتى عشر دقائق. التطبيق يعمل على loopback `127.0.0.1:5187` فقط. لا تضبط الخيار في التشغيل التلقائي العادي. بيئة العزل قد تمنع مفاتيح ASP.NET المحلية وWindows Event Log؛ الاختبار الفعلي تم بصلاحيات المستخدم المعتادة.
