# دراسة: إدارة الصلاحيات والأدوار — أدوار جاهزة + مخصصة

التاريخ: 2026-11-08 · الحالة: دراسة قبل التنفيذ (لم تُعتمد بعد)

## 1. تشخيص الوضع الحالي

- `Role` كيان فعلي (`roles` + `role_permissions`، مفتاح مركب على `(RoleId, Feature)`، المستويات مخزّنة نصاً).
- `PermissionLevel = None | Read | Write` فقط (`Domain\Enums\PermissionLevel.cs`).
- `PermissionFeature`: 14 خاصية ثابتة في الكود (enum غير قابل للتوسع من DB).
- `AuthorizationService.IsAllowedAsync` (`Application\Authorization`): `User.IsAdmin == true` ⇒ تجاوز كامل؛ وإلا يُقرأ مستوى الخاصية من الدور المُسند لكل طلب (DB، لا صلاحيات في الـ cookie).
- لا يوجد أي Seed للأدوار أياً: التثبيت الأول = صفر أدوار، فكل إضافة مستخدم تفتح أسئلة «أنشئ دوراً؟ ما مستوى كل خاصية؟».
- `IsAdmin` مفتاح منطقي مستقل عن الدور بمستوى واحد (مستخدم/مدير). لا يوجد أي منطق اعتماد أو مراجعة في الكود.
- الصفحات: `/admin/roles` (قائمة)، `/admin/roles/create|edit` (مصفوفة `RolePermissionCards`)، و`RoleEditorDialog` يُفتح من صفحة إنشاء مستخدم.

الألم المطروح من المالك:
1. عند كل إضافة مستخدم: اختيار دور أو إنشاء دور وتحديد مستوى كل خاصية — مزعج ويسبب لبساً.
2. `IsAdmin` قيمة منطقية يسهل تغافلها، وبمستوى واحد فقط (مستخدم أو مدير).
3. مستقبلاً: عمليات تحتاج موافقة من مستخدم «أعلى».

## 2. المتعارف عليه في الصناعة

| نمط | المعنى | أمثلة |
|---|---|---|
| **أدوار مبنية مسبقاً (Built-in / Sealed)** | أدوار جاهزة تطابق سير العمل، **ثابتة: لا تعديل ولا حذف**، تجعل النظام صالحاً من اللحظة الأولى | Microsoft Entra (built-in roles بتعريف ثابت)، CloudBees (Admin/Approver/User)، Laravel Cloud (predefined roles)، Odoo (مجموعات جاهزة: Sales/Purchases/Accounting/Administrator) |
| **أدوار مخصصة (Custom)** | نفس نظام الصلاحيات لكن تركيب حر — لتغطية الحالات الشاذة فقط | كل الأنظمة أعلاه |
| **الحد الأدنى للصلاحية ومنع تضخم الأدوار** | الأدوار تعبّر عن مسؤوليات ثابتة لا حالات شخصية؛ الجاهز هو مرجع التأليف والمخصص استثناء موثق | أدلة Enterprise RBAC 2026 (Role Explosion أكبر فشل متكرر) |
| **فصل المهام (SoD)** | مُدخل البيانات ≠ المعتمِد؛ «الاعتماد» مستوى صلاحية منفصل عن القراءة/الكتابة | دور Approver مستقل في كل الدلائل |
| **سلطة الاعتماد بمستوى لا بشخص** | الموافقة تُفعَّل بمستوى (Approve)؛ التدرّج لاحقاً بمصفوفة اعتماد وليس بترقية flag المدير | أدلة سير العمل |
| **superuser واحد دائم = خطأ شائع** | «مدير مشلّ للصلاحيات كلها» يخفي الوصول عالي الأثر ويقوّض المراجعات؛ الحل: مدير تشغيلي (دور مغلق) + مدير أعلى (flag) بمعنى صريح | ذُكر حرفياً في أدلة تصميم RBAC |

الخلاصة: مقترح المالك (أدوار جاهزة مغلقة + دور مخصص + تفريق مدير/مدير أعلى) هو النمط القياسي نفسه، والناقص فقط هو مستوى «اعتماد» لفصل مُدخل البيانات عن المعتمِد مستقبلاً.

## 3. الأدوار الجاهزة المقترحة (مغلقة)

تُوزع بإضافة عمودين على `roles`: **`IsSealed`** (bool، default false) و **`RoleKey`** (varchar فريد nullable مثل `sales`). المفتاح النصي يحمي الـ Seed من تضارب تسلسل المعرفات مع الأدوار المخصصة.

| الدور | RoleKey | التكوين المقترح (على أعمدة الـ14) |
|---|---|---|
| **مبيعات** | `sales` | Orders=Write، Clients=Write، Documents=Read، Products/Categories/Cities/PaymentMethods/Deliverymen/ShippingCarriers=Read |
| **مشتريات** | `purchasing` | Suppliers=Write، Orders=Read، Documents=Read، Products/Cities/PaymentMethods=Read |
| **إدخال البيانات** | `data-entry` | Products/Categories/Properties/Cities=Write، PaymentMethods=Read، Orders=لا شيء |
| **محاسب** (يُنشأ جاهزاً، يُفعَّل عند الحاجة) | `accounting` | Documents=Write، PaymentMethods=Write، Orders/Clients/Suppliers/Products=Read، Settings=Read، البقية=None |
| **مدير** | `manager` | كل خاصيات التشغيل (Orders → PaymentMethods) = **Approve**، Users=Write، Logs=Read، Settings=Read |
| **مدير أعلى** | لا دور — `IsAdmin` (تجاوز كامل دائم) | كما اليوم، بخلفية واجهة صريحة انظر §5 |

ملاحظات المصفوفة:
- «إدخال البيانات» بلا وصول للطلبات عمداً — تجسيد لفصل المهام.
- «المحاسب» يُنشأ مغلقاً الآن ليكون جاهزاً عند تفعيل التدفقات المالية لاحقاً دون إعادة تصميم.
- هذه المصفوفة نقطة بداية — توافقها النهائي مع المالك قبل الـ Migration.

## 4. مستوى «اعتماد» (Approve) — الباب المستقبلي

توسيع `PermissionLevel` إلى `None < Read < Write < Approve`:
- تراتبية: `Read` يحققه Read|Write|Approve، `Write` يحققه Write|Approve، `Approve` بالـApprove وحده. تغيير صغير في `AuthorizationService.IsAllowedAsync` (سطر switch) وأي switch آخر يبني على `PermissionLevel`.
- التخزين نصّي (`varchar(20)`) ⇒ إضافة العضو لا تتطلب تغيير عمود في الـ Migration.
- `RolePermissionCards`/`MudToggleGroup` تنتقل من 3 شرائح إلى 4.
- عند بناء تدفقات الاعتماد لاحقاً: أي أمر «اعتماد» يعلم بـ `[RequirePermission(Feature, Approve)]` ويعمل مباشرة دون تعديل مصفوفة الصلاحيات. رتبة «أعلى» متى احتاجت تُبنى كحد على التدفق، لا على `IsAdmin`.

## 5. إعادة صياغة «مدير النظام»

الإبقاء على `IsAdmin` (لا هجرة فورية) مع إصلاح معناه وعرضه:
- إعادة تسميته في الواجهة **«مدير أعلى»** بوصف صريح: «هذا الحساب يتجاوز جميع الأدوار والصلاحيات، بما فيها إدارة المستخدمين والاعتمادات».
- عرضه **كخيار نوع الحساب** في صفحة المستخدم، لا مربع اختيار جانبي يسهل تغافله.
- «المدير» التشغيلي يصبح دور `manager` المغلق (Approve على التشغيل + Users=Write) — يدير الفريق دون مفاتيح النظام.
- لاستئصال اللبس: المستخدم إما **دور مُسند** (جاهز أو مخصص) أو **مدير أعلى**؛ الواجهة تُعطّل اختيار الدور عند تفعيل المدير الأعلى بدل السماح بتركيب خليط بلا معنى.

## 6. إغلاق الأدوار الجاهزة (غير قابلة للتعديل أو الحذف)

- `Domain\Role`: خاصية `IsSealed` مع حمايات في `Rename`/`SetPermission` (استثناء «Role is sealed»)، ومعرّف `RoleKey`.
- Application: حراسة في أوامر إنشاء/تحديث/حذف الأدوار (الحذف محجوب أصلاً بـ FK Restrict من `users`، لكن يُعلن مسبقاً في الواجهة).
- Infrastructure: Migration (تسمية تنازلية مثل `20261108000000_SeedSealedRoles`): إضافة `is_sealed` + `role_key` + فهرس فريد، ثم Seed يُطابق بالـ `role_key` (upsert لا يلمس أدوار المستخدمين).
- Web: شارة «دور جاهز» في القائمة، وتعطيل المصفوفة والتعديل/الحذف للمغلق.
- اختبارات SQLite: حراسات الكيان + الصفوف المزروعة تختبر في SQLite بلا حواجز إضافية من snake_case.

## 7. حل إرهاق إضافة المستخدم (اللبس)

صفحة إنشاء/تعديل المستخدم تنتقل من «اختر دوراً أو أنشئه بنفسك» إلى:
1. **قائمة مقسمة**: «أدوار جاهزة» (مبيعات/مشتريات/إدخال بيانات/محاسب/مدير) ثم «أدوار مخصصة»، وخيار «مدير أعلى».
2. **بطاقة معاينة**: عند اختيار الدور تُلخّص صلاحياته بعدّادات لكل مستوى فيُدرك المعنى قبل الحفظ.
3. **«دور مخصص انطلاقاً من قالب»**: الدور المخصص يبدأ منسوخاً من دور جاهز (نسخ + تعديل) بدل مصفوفة فارغة — يخفّض مجهود الإعداد ويقاوم تضخم الأدوار.
4. اختيار «مدير أعلى» يُطفئ اختيار الدور (انظر §5).

`RoleEditorDialog` القائم يبقى لكنه يفتح بوضع «من القالب».

## 8. خطة التنفيذ (تكاليف تقديرية)

| المرحلة | المجالات | الحجم |
|---|---|---|
| 1. توسيع `Approve` | Domain (enum + تحقق RolePermission)، Application (AuthorizationService)، UI المصفوفة، اختبارات | صغيرة |
| 2. أدوار مغلقة + Seed | Domain (IsSealed/RoleKey)، Migration، حراسات Application، UI الشارة/التعطيل، اختبارات | متوسطة |
| 3. واجهة المستخدم | صفحة المستخدم (قائمة مقسمة + معاينة + قالب + فصل المدير الأعلى)، تسميات المدير الأعلى | متوسطة |
| 4. (لاحقاً، مشروع مستقل) تدفقات الاعتماد | اعتمادات الطلبات/المستندات على مستوى `Approve` | مشروع قائم بذاته |

اتجاه التأثير (House rule 4): enum Domain → AuthorizationService Application → Migration Infrastructure → صفحات Web.

## 9. قرارات مطلوبة من المالك

1. مراجعة المصفوفة النهائية للأدوار الخمسة الجاهزة في §3 (مثلاً: هل «المدير» يدير المستخدمين بـ Write أم Read فقط).
2. مستوى `Approve`: إضافته في هذه الدفعة (توصية — يفتح المستقبل بأقل تكلفة) أم تأجيله؟
3. «مدير أعلى»: إبقاء `IsAdmin` مع إعادة عرض وتسمية (توصية) أم تحويله إلى دور مغلق حقيقي؟
4. «إنشاء من قالب» للدور المخصص: نعم (توصية) أم مصفوفة فارغة فقط؟
5. «المحاسب»: يُغلق الآن ضمن الـ Seed أم يُؤجل إلى حاجته؟
